# 交易环节二次自查与兜底方案

> 日期：2026-07-31
> 范围：购物车、结算、订单、库存、支付、发货、售后、数据库迁移与运行环境
> 结论：当前交易链路可用于 Demo 和内部验收，在 P0 问题关闭前不得开放真实支付与自动履约。

## 1. 本次完成的检查

1. 阅读交易剩余工作、交易验收方案、商品真实接口与数据库迁移规格。
2. 静态检查交易模块 Controller、Service、DO、SQL、Spring Security 和 Docker 配置。
3. 使用 Java 25 Docker 构建环境完成 Maven 编译和现有测试。
4. 运行 `scripts/verify-trade-flow.ps1`，验证下单、支付、发货、收货、售后和超时关闭主流程。
5. 在隔离数据库复现购物车重复购买时的软删除唯一键冲突。
6. 通过真实接口验证匿名管理端访问、不存在商品回退 Mock、退款状态与库存不一致。
7. 运行数据库迁移验收脚本，确认后续迁移已经破坏原有验收基线。
8. 清理全部审计测试用户、商品、购物车和订单，删除临时后端并恢复 MySQL、Redis 原状态。

## 2. 实际验证结果

### 2.1 通过项

- Java 25 容器内 Maven 构建成功。
- 现有 7 个商品模块测试全部通过。
- 现有交易主流程自动验收脚本通过。
- 超时关闭、库存回补、发货、确认收货、售后同意/拒绝/撤销的既有脚本场景可运行。

### 2.2 测试覆盖缺口

- 交易模块没有单元测试，Maven 输出为 `No tests to run`。
- 现有交易验收脚本未覆盖鉴权、真实 SKU、同一商品重复购买、支付单金额一致性、退款库存回补和并发状态竞争。
- Dockerfile 使用 `-DskipTests` 构建，镜像构建成功不能代表交易测试通过。

## 3. P0 问题

### P0-1 管理端接口匿名开放

`SecurityAutoConfiguration` 对 `/admin-api/**` 使用 `permitAll()`。实测未登录即可读取订单、收货人、手机号、地址，也可调用发货和售后审批接口。

### P0-2 Mock 变更接口没有后端开关

以下接口只在小程序前端隐藏，后端始终可调用：

- `/app-api/pay/mock-success`
- `/app-api/order/mock-ship`
- `/app-api/order/refund/mock-approve`

登录用户可绕过真实支付、发货和退款审核流程。

### P0-3 交易未接入真实 SKU

- 交易使用 `goodsId * 1000000000 + productId` 合成 SKU ID。
- 价格、库存仍读取 `product_spu`，没有读取 `product_sku`。
- 任意 `productId` 可能被接受。
- 数据库商品不存在时仍回退 `MockData`。实测虚构商品可以成功加入购物车。

### P0-4 下单价格使用购物车旧快照

提交订单时虽然重新查询商品并扣库存，但订单金额和订单明细仍使用购物车保存的旧价格。商品调价后，用户可能继续按旧价格下单。

### P0-5 购物车重复购买冲突

`trade_cart` 使用逻辑删除，同时唯一键为 `(user_id, sku_id, deleted)`。隔离数据库实测：

1. 第一次加入商品并软删除；
2. 第二次加入同一 SKU；
3. 第二次软删除时触发 `Duplicate entry`；
4. 下单事务可能因此整体回滚。

### P0-6 退款数据不一致

实测待发货订单退款后：

- `trade_order.status=5`
- `trade_order.pay_status=2`
- `pay_order.status` 仍为 `1`
- 商品库存从 10 扣到 9 后没有恢复
- `/app-api/pay/query` 返回“未支付”

管理端退款审批还允许在没有售后申请时自动创建售后单并直接退款。

## 4. P1 稳定性问题

- 下单没有幂等键，并发提交可能生成重复订单并重复扣库存。
- 支付单没有 `order_id` 唯一约束，预支付并发可能产生重复支付单。
- 支付单金额与订单实付金额没有强制一致性校验。
- 发货、确认收货、售后同意/拒绝/撤销多处采用先查询再无条件更新，存在状态覆盖风险。
- 用户订单列表和售后列表存在全量查询后内存分页，订单列表还有 N+1 查询。
- 订单号采用秒级时间加四位随机数，高并发下存在唯一键冲突概率。

## 5. 数据库与运行环境问题

### 5.1 迁移验收失效

`scripts/verify-db-migration.ps1` 当前执行失败：

- 临时基线缺少 `content_banner`，首页内容迁移中断；
- 仓库已有三个迁移版本，但脚本仍断言迁移历史总数为一条。

当前迁移脚本不得直接用于客户数据库，必须先修复并在数据库克隆环境验证。

### 5.2 Docker Mock 登录配置失效

- Dockerfile 命令行强制激活 `prod`；
- `application-prod.yml` 将微信 Mock 登录写死为 `false`；
- Compose 配置的 `WX_MA_MOCK_ENABLED=true` 实际不会覆盖该配置。

因此文档中的“Docker 默认使用 Mock 微信登录”与实际运行结果不一致。

## 6. 立即兜底方案

1. 在网关阻断 `/admin-api/**` 的公网访问，仅允许内网或临时 IP 白名单。
2. 非开发环境关闭三个 Mock 变更接口；真实微信支付完成前，将商城切换为只浏览或暂停支付。
3. 暂停自动退款审批，执行订单、支付单、退款单和库存四项人工复核。
4. 多规格商品暂时不进入交易，只开放经过白名单验证的单规格商品。
5. 客户数据库禁止直接运行当前迁移脚本；先备份，再在数据库克隆环境验证。
6. 建立每日对账清单，检查订单状态、支付单状态、退款状态和库存变化是否一致。

## 7. 正式修复顺序

1. 管理端登录、RBAC、真实操作人审计和 Mock 接口环境隔离。
2. 真实 SKU 查询、实时价格校验、SKU 原子扣减和库存回补。
3. 下单幂等键、支付单唯一约束、支付金额校验和重复回调处理。
4. 修复购物车逻辑删除唯一键，交易购物车优先改为物理删除。
5. 退款事务统一更新订单、支付单和库存，并增加失败补偿与对账任务。
6. 修复迁移验收和 Docker 配置，再补交易单元测试、集成测试与并发测试。

## 8. 上线门禁

以下条件全部满足后，才允许接入真实资金：

- 管理端接口不能匿名访问；
- 生产环境不存在可调用的 Mock 支付、发货和退款入口；
- 下单只接受数据库中真实存在且已上架的 SKU；
- 订单、支付单、退款单和库存状态保持一致；
- 重复提交、重复回调和并发状态切换具备幂等保障；
- 数据库迁移和交易回归脚本在隔离环境持续通过。
