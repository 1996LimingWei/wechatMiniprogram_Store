# 商品与交易可交付化实施计划

> 日期：2026-08-01  
> 目标：将当前“可演示的交易 MVP”提升为“可稳定联调，并具备接入真实支付前置条件”的版本。  
> 依据：[商品真实接口与本地数据库迁移设计](../specs/2026-07-27-product-real-api-and-migration-design.md)、[交易审计与兜底方案](trade-audit-and-fallback.md)。

## 1. 交付里程碑

| 里程碑 | 完成定义 | 当前状态 |
| --- | --- | --- |
| M1：安全可演示 | 管理操作受鉴权保护；非开发环境无法调用 Mock 变更接口；迁移与回归可重复执行 | 未开始 |
| M2：真实商品可交易 | 只允许已上架真实 SKU 下单，按 SKU 校验价格与扣减/回补库存 | 未开始 |
| M3：稳定联调 | 商品、购物车、订单、支付、退款的数据一致性通过自动化与并发验收 | 未开始 |
| M4：真实资金上线准备 | 微信支付 V3/退款适配完成，生产配置、对账和上线门禁具备 | 依赖客户资料 |

## 2. 执行顺序与任务拆分

### 阶段 A：P0 安全止血与验收基线（M1）

1. 管理端鉴权与审计
   - 收紧 `/admin-api/**`，仅经管理员登录和 RBAC 授权的用户可访问。
   - 管理端发货、售后审批写入操作人、操作时间和订单日志。
2. Mock 操作环境隔离
   - 将 Mock 支付成功、模拟发货、模拟退款审核限制为 `dev`/`test` 环境，并在生产配置中硬性禁用。
   - 小程序移除面向用户的 Mock 文案和操作入口。
3. 修复验收基础设施
   - 修复 `verify-db-migration.ps1` 的迁移基线及动态版本断言。
   - 修复 Docker 的 Mock 微信登录配置，使 Compose 环境与文档一致。
4. 阶段验收
   - 匿名访问管理接口返回 401/403。
   - 生产 profile 调用三个 Mock 变更接口被拒绝。
   - 迁移在空库、升级库各连续执行两次均成功。

### 阶段 B：商品、SKU 与库存真实化（M2）

1. 商品模型与种子数据
   - 补齐 `product_sku` 的规格、售价、库存、上下架状态和商品图片数据；整理演示种子数据。
   - 禁止商品不存在时回退 `MockData`。
2. 商品读取链路
   - 分类、列表、关键词搜索、详情、规格选择均从数据库读取；筛选与分页在数据库完成。
3. 交易商品快照与库存接口
   - 交易服务仅通过商品服务读取真实 SKU 快照、实时价格与可售状态。
   - 下单按 SKU 原子扣库存；取消、超时关闭、退款按业务状态只回补一次。
4. 阶段验收
   - 虚构商品或无效规格不能加入购物车/下单。
   - 调价后结算和下单使用实时价；订单保存不可变商品快照。
   - 多规格商品库存分别扣减，不超卖、不重复回补。

### 阶段 C：交易一致性与稳定性（M3）

1. 修复交易 P0 数据问题
   - 购物车改为物理删除，或调整唯一键以消除逻辑删除重复购买冲突。
   - 退款使用单一事务同步更新订单、支付单、退款单和库存；失败场景进入可对账的补偿流程。
   - 禁止无售后申请直接退款。
2. 补齐幂等与并发保护
   - 下单增加幂等键；支付单增加订单唯一约束和金额强校验。
   - 发货、收货、售后审批改为条件更新，避免并发覆盖状态。
   - 订单号生成改为可验证的全局唯一方案。
3. 回归测试与性能基础
   - 将支付状态机已有测试纳入模块回归；新增购物车、库存、退款、鉴权和并发集成测试。
   - 订单/售后查询使用数据库分页，并补齐必要索引。
4. 阶段验收
   - 重复下单、重复回调、关闭与支付竞争、重复退款均不产生重复扣减、日志或退款。
   - 自动交易验收覆盖下单至售后全流程，并在隔离数据库持续通过。

### 阶段 D：真实支付与上线准备（M4）

1. 接入微信支付 V3 的预下单、回调验签、退款与退款回调。
2. 建立订单、支付单、退款单、库存的每日对账与异常告警。
3. 完成生产配置、密钥管理、回调域名、备份恢复演练与上线回滚方案。
4. 仅当客户提供 AppID、商户号、API v3 密钥、证书和回调域名后启动本阶段。

## 3. 推荐分工

| 角色 | 主责 | 不应并行修改的范围 |
| --- | --- | --- |
| 商品负责人（Tim） | 阶段 B：SKU 数据模型、商品读取、规格选择、商品快照契约 | 不直接修改订单状态机和支付回调 |
| 交易负责人 | 阶段 C：库存协作、退款一致性、幂等、订单索引与回归 | 不改商品页面和商品迁移所有权范围 |
| 平台/管理端负责人 | 阶段 A：RBAC、Mock 环境隔离、管理端操作审计、Docker/迁移基线 | 不改变商品/交易核心业务规则 |

## 4. 工作规则

1. 每阶段先创建独立 spec/plan 与功能分支，再开始编码。
2. 数据库只新增版本化迁移，不修改已发布迁移，不对已有库重跑 `init.sql`。
3. 每个阶段合并前必须完成模块测试、全量构建和隔离数据库验收。
4. 未完成 M1 至 M3 前，不接真实支付、不开放自动履约，也不将数据库迁移直接用于客户库。

## 5. 近期第一步

先启动阶段 A 的“管理端鉴权 + Mock 接口环境隔离”子任务；它不依赖 SKU 设计，却能立即消除匿名操作与测试接口外露风险。阶段 A 完成后，Tim 开始阶段 B 的 SKU 数据模型与真实库存链路。
