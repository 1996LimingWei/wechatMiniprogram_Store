# 交易模块剩余工作清单

> 日期：2026-07-26  
> 范围：微信小程序商城的交易闭环  
> 目标：明确从“测试阶段可跑通”到“企业客户可验收、可交付”的剩余工作，不等问题出现后再补。

---

## 1. 当前交易模块已经完成什么

当前交易主流程已经具备 MVP 能力：

1. 购物车
   - 加入购物车
   - 购物车列表
   - 修改数量
   - 删除商品
   - 勾选商品
   - 立即购买与购物车结算隔离

2. 地址
   - 地址列表
   - 地址新增/编辑
   - 地址删除
   - 默认地址
   - 结算页选择地址

3. 结算与下单
   - 选中商品结算
   - 商品金额、运费、订单金额计算
   - 提交订单
   - 下单扣库存
   - 清理已结算购物车

4. 支付
   - Mock 预支付
   - Mock 支付成功
   - 支付状态查询
   - 已支付订单禁止重复支付
   - 已取消订单禁止支付
   - 支付成功条件更新，避免和超时关闭互相覆盖

5. 订单流转
   - 待付款
   - 待发货
   - 待收货
   - 已完成
   - 已取消
   - 退款中
   - 已退款

6. 发货与物流
   - 模拟发货
   - 物流公司和物流单号保存
   - 订单详情/列表返回物流信息
   - 物流轨迹 Mock 展示

7. 售后与退款
   - 申请退款/售后
   - 售后详情
   - Mock 退款审核通过
   - 支付状态更新为已退款

8. 超时关闭与库存释放
   - 待付款订单默认 30 分钟超时
   - 定时任务自动关闭超时未支付订单
   - 超时关闭后回补库存
   - 超时关闭后关闭待支付支付单
   - 重复扫描不会重复回补库存

9. 订单状态日志
   - 提交订单
   - 支付成功
   - 用户取消
   - 系统超时关闭
   - 发货
   - 确认收货
   - 申请售后
   - 退款完成

## 2. 判断标准：测试阶段 vs 企业交付

测试阶段允许：

- 使用 Mock 商品数据
- 使用 Mock 支付
- 使用 Mock 物流
- 使用 Mock 退款
- 使用开发用按钮推动流程

企业交付至少要求：

- 交易流程有明确状态机
- 关键操作有日志
- 异常场景能兜底
- 管理端有商家处理入口
- 用户端不暴露内部/模拟操作
- 验收流程可以重复执行
- 数据库结构清晰且可迁移
- 与商品、支付、营销、后台模块的职责边界明确

## 3. P0 必须做：不做会影响企业验收

### P0-1 管理端订单处理接口

**现状**

现在发货、退款审核等操作还在小程序端通过模拟按钮触发。测试阶段能用，但企业客户验收时必须有“商家/运营处理订单”的能力。

**需要做**

1. 管理端订单列表接口
   - 路径建议：`/admin-api/trade/order/list`
   - 支持按订单号、用户、订单状态、支付状态、时间范围筛选
   - 支持分页

2. 管理端订单详情接口
   - 路径建议：`/admin-api/trade/order/detail`
   - 返回订单基础信息、收货信息、商品明细、支付信息、物流信息、售后信息、订单日志

3. 管理端发货接口
   - 路径建议：`/admin-api/trade/order/ship`
   - 输入订单 ID、物流公司、物流单号
   - 仅允许待发货订单发货
   - 发货后订单变为待收货
   - 写入订单日志

4. 管理端售后列表接口
   - 路径建议：`/admin-api/trade/after-sale/list`
   - 支持处理中、已退款、已拒绝筛选

5. 管理端售后审核接口
   - 路径建议：`/admin-api/trade/after-sale/approve`
   - 路径建议：`/admin-api/trade/after-sale/reject`
   - 同意后进入退款完成
   - 拒绝后售后状态变为已拒绝，订单恢复到可展示状态
   - 写入订单日志

**验收标准**

- 小程序用户下单支付后，管理端能查到待发货订单
- 管理端发货后，小程序端显示待收货并能查看物流
- 用户申请售后后，管理端能查到售后单
- 管理端同意退款后，小程序端显示已退款
- 管理端拒绝退款后，小程序端能看到售后被拒绝
- 所有管理端操作都有订单日志

**优先级**

最高。建议下一步先做。

---

### P0-2 用户端开发按钮收口

**现状**

小程序订单列表/详情里存在：

- 模拟发货
- 模拟退款通过

这些按钮测试阶段可用，但企业验收时必须收口。

**需要做**

1. 开发环境可以保留
   - 通过配置控制，例如 `isDevTradeActionEnabled`
   - 开发模式显示，非开发模式隐藏

2. 普通用户端必须隐藏
   - 用户只能看到：支付、取消、查看物流、确认收货、申请售后
   - 用户不能看到：发货、审核退款、模拟通过

3. 文案收口
   - 页面里不能出现“Mock”“模拟”“开发中”等面向内部开发的字样

**验收标准**

- 普通用户视角没有“模拟发货”“模拟退款通过”
- 测试环境如需保留，可以通过明确配置打开
- 客户演示时不会暴露开发痕迹

**优先级**

最高。建议和管理端接口一起做。

---

### P0-3 交易验收文档与自动验收脚本

**现状**

目前交易流程依赖手动测试。功能越多，越容易出现“某一步改完影响另一条路径”的问题。

**需要做**

1. 交易验收文档
   - 文件建议：`docs/superpowers/plans/2026-07-26-trade-acceptance.md`
   - 覆盖购物车下单、立即购买、取消、超时关闭、支付、发货、确认收货、售后退款、订单日志

2. 自动验收脚本
   - 文件建议：`scripts/verify-trade-flow.ps1`
   - 自动创建测试用户、测试商品、测试地址、测试订单
   - 自动跑完整交易流程
   - 自动断言订单状态、支付状态、库存、支付单、订单日志
   - 最后自动清理测试数据

**验收标准**

- 一条命令可以跑完交易主流程
- 脚本失败时能明确指出哪一步失败
- 测试数据不污染客户/演示数据
- 团队成员能按文档独立验收

**优先级**

最高。企业交付必须有固定验收标准。

---

### P0-4 售后拒绝与撤销能力

**现状**

售后目前只有：

- 用户申请
- Mock 审核通过

还缺企业常见的：

- 商家拒绝
- 用户撤销
- 拒绝原因
- 售后状态恢复

**需要做**

1. 售后拒绝
   - 售后状态：处理中 -> 已拒绝
   - 保存拒绝原因
   - 订单状态从退款中恢复到原业务状态

2. 用户撤销售后
   - 售后状态：处理中 -> 已撤销
   - 订单状态恢复

3. 售后表补字段
   - `reject_reason`
   - `cancel_time`
   - `reject_time`
   - `before_order_status`

**验收标准**

- 订单申请售后后，可以被拒绝
- 拒绝后订单不应一直停留在退款中
- 用户撤销后订单恢复正常
- 拒绝/撤销写入订单日志

**优先级**

高。否则售后一旦申请，只能通过，流程不完整。

## 4. P1 应该做：影响稳定性和后续扩展

### P1-1 支付状态机整理

**现状**

当前 Mock 支付可用，但支付逻辑还没有独立状态机文档，也没有完整覆盖异常组合。

**需要做**

1. 明确支付单状态
   - 待支付
   - 已支付
   - 已关闭
   - 已退款

2. 明确订单状态与支付状态关系
   - 待付款 + 未支付
   - 待发货/待收货/已完成 + 已支付
   - 已取消 + 未支付
   - 退款中 + 已支付
   - 退款中 + 已退款

3. 补异常兜底
   - 支付单已关闭时再次预支付如何处理
   - 支付单金额与订单金额不一致如何处理
   - 支付成功重复回调如何处理
   - 支付成功但订单状态已取消如何处理
   - 支付成功与超时关闭并发如何处理

**验收标准**

- 每个状态组合都有明确处理规则
- 重复支付不会重复改变订单
- 已关闭订单不会被支付成功改回待发货
- 支付单和订单金额不一致会拒绝处理

---

### P1-2 库存边界与商品模块对接

**现状**

交易模块现在直接扣 `product_spu.stock`。短期可以跑，但商品真实接口由另一位同事负责，后续必须明确边界。

**需要做**

1. 明确交易调用商品模块的库存接口
   - 查询商品快照
   - 校验商品上下架
   - 扣库存
   - 回补库存

2. 明确库存回补规则
   - 待付款取消：回补
   - 待付款超时关闭：回补
   - 待发货退款：建议回补
   - 待收货退款：是否回补取决于是否退货入库
   - 已完成退款：一般不自动回补，需售后入库动作

3. SKU 级库存
   - 当前主要按 SPU 扣库存
   - 商品真实化后必须对接 SKU 库存，否则多规格商品会不准确

**验收标准**

- 下单不能超卖
- 取消/超时不会重复回补
- 商品下架后不能下单
- 多规格商品按 SKU 扣库存

---

### P1-3 订单搜索与分页性能

**现状**

订单列表目前能查，但企业订单量上来后，需要更严谨的查询字段和索引。

**需要做**

1. 后端订单列表支持筛选
   - 订单号
   - 用户 ID
   - 手机号
   - 订单状态
   - 支付状态
   - 创建时间

2. SQL 索引补强
   - `order_sn`
   - `user_id`
   - `status`
   - `pay_status`
   - `create_time`
   - 管理端组合索引

3. 分页必须走数据库分页
   - 不能查全部后再内存分页

**验收标准**

- 管理端订单列表分页稳定
- 订单量变大后查询不明显卡顿
- 查询条件命中索引

---

### P1-4 订单详情数据完整性

**现状**

订单详情已经返回基础订单信息、商品、物流、售后、日志，但企业交付还需要更多字段完整展示。

**需要做**

1. 订单详情补充
   - 订单号
   - 下单时间
   - 支付时间
   - 关闭时间
   - 关闭原因
   - 收货地址快照
   - 商品快照
   - 运费
   - 优惠金额
   - 实付金额
   - 支付单信息
   - 售后单信息
   - 订单日志

2. 前端展示整理
   - 小程序详情页展示必要字段
   - 管理端详情页展示完整字段

**验收标准**

- 客服/运营只看订单详情即可判断订单当前情况
- 订单历史信息不依赖商品实时数据
- 地址和商品改名后，历史订单仍保持下单时快照

## 5. P2 可后置：增强体验或真实化能力

### P2-1 优惠券与价格计算

**现状**

前端已有优惠券入口，但后端结算里 `couponPrice=0`，`couponList` 为空。

**需要做**

- 优惠券表

### P2-4 评价闭环

**现状**

## 6. 建议的执行顺序

### 第一步：管理端最小订单处理接口

先做：

1. 管理端订单列表
2. 管理端订单详情
3. 管理端发货
4. 管理端售后列表
5. 管理端同意/拒绝售后

原因：这是企业交易系统最核心的“商家处理订单”能力。

### 第二步：用户端开发按钮收口

把小程序端的模拟操作隐藏或移除：

1. 隐藏模拟发货
2. 隐藏模拟退款通过
3. 保留正常用户动作

原因：避免客户验收时看到内部测试痕迹。

### 第三步：交易验收文档与自动脚本

做：

1. `trade-acceptance.md`
2. `scripts/verify-trade-flow.ps1`

原因：交易功能越来越多，必须有可重复验收标准。

### 第四步：售后拒绝/撤销

补：

1. 拒绝售后
2. 撤销售后
3. 订单状态恢复
4. 日志记录

原因：售后不能只有“通过”一种结果。

### 第五步：支付、库存、优惠券、物流真实化

按客户资料和其他同事进度推进：

1. 微信支付
2. SKU 库存对接
3. 优惠券
4. 真实物流
5. 评价
