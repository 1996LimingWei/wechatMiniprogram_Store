# 支付状态机与异常幂等性设计

> 日期：2026-07-30
> 类型：交易 P1 设计规格
> 对应 Issue：#14

## 1. 背景与目标

交易 P0 已具备 Mock 预支付、支付成功、超时关闭与退款的基础能力，但支付单状态、订单支付状态和异常路径尚未由一套明确规则约束。该 Issue 的目标是收敛这些状态转换，使重复回调、订单关闭后回调和金额不一致等异常不会改变订单的正确终态。

## 2. 状态定义

支付单 `pay_order.status`：

| 值 | 状态 | 含义 |
| --- | --- | --- |
| 0 | 待支付 | 已创建支付单，尚未确认支付 |
| 1 | 已支付 | 已确认支付成功 |
| 2 | 已关闭 | 用户取消或订单超时后关闭，不能再次支付 |
| 3 | 已退款 | 已支付订单完成退款 |

订单 `trade_order.status` 与 `pay_status` 必须保持以下合法组合：

| 订单状态 | 支付状态 | 说明 |
| --- | --- | --- |
| 待付款（0） | 未支付（0） | 允许创建或复用待支付单 |
| 待发货/待收货/已完成（1/2/3） | 已支付（1） | 支付成功后的正常订单 |
| 已取消（4） | 未支付（0）或已退款（2） | 关闭未支付订单或已退款订单 |
| 退款中（5） | 已支付（1） | 售后处理期间 |

## 3. 业务规则

1. 预支付只允许“待付款 + 未支付”订单创建或复用一张待支付支付单；已支付、已关闭和已退款支付单均不得重开。
2. 支付成功必须以支付单、订单归属、金额和可支付状态为前提；订单金额与支付单金额不一致时拒绝处理并保留原状态。
3. 同一支付成功回调重复到达时，首次完成状态转换并记录一次日志，后续请求返回成功但不重复写订单、支付单、库存或日志。
4. 用户取消或系统超时关闭未支付订单时，订单与对应待支付支付单必须在同一事务中关闭；后续支付成功回调必须被拒绝，订单不得回到待发货。
5. 已支付订单退款完成时，支付单从“已支付”转为“已退款”；退款重复通知不得重复记录状态变化。
6. 每次实际状态转换均记录订单日志；幂等命中和被拒绝的无效回调不新增成功日志。

## 4. 范围与边界

本 Issue 仅修改 `shop-module-trade` 的支付域、交易迁移、测试和文档。继续保留现有 `/app-api/pay/prepay`、`/app-api/pay/mock-success`、`/app-api/pay/query` 路径及 Mock 支付参数。

不在范围内：微信支付 V3、真实退款、SKU 库存接口、商品快照重构、首页内容、收藏、足迹、评论和任何小程序页面改动。这些边界确保可与 Issue #13 并行开发。

## 5. 验收标准

- 状态矩阵及所有转换规则在文档和代码中一致。
- 重复支付成功、关闭后支付、金额不一致、支付与超时关闭竞争四类场景均有自动化测试。
- 订单关闭后支付单状态为“已关闭”，支付成功不会复活订单；重复成功回调只产生一条支付成功日志。
- JDK 25 环境下执行 `cd shop-backend && mvn test -pl shop-module-trade -am` 通过。
