# Mock 契约优先与可替换数据源设计

> 日期：2026-08-01  
> 状态：已确认  
> 目标：先用完整 Mock 数据完成全量页面和业务流程，再在不改变小程序 API、Controller 和交易规则的前提下，逐项替换为数据库或第三方真实数据源。

## 1. 核心原则

1. Mock 替代的是数据来源，不替代业务规则。
2. 小程序只调用稳定的正式 API；不得因 Mock/真实模式切换不同路径、字段或前端判断分支。
3. Controller 仅负责请求与响应；商品、库存、支付、物流等通过明确服务契约取得能力。
4. Mock、数据库和第三方实现必须遵守同一服务契约，并用同一组验收用例验证。
5. 生产环境禁止任何会改变订单、支付、库存或退款状态的 Mock 实现。

## 2. 可替换能力边界

| 能力 | 统一契约 | Mock 阶段 | 真实替换阶段 |
| --- | --- | --- | --- |
| 商品与 SKU | 查询商品、规格、价格、可售状态、快照 | 固定且可复现的演示商品集 | MySQL 商品/SKU 表 |
| 库存 | 校验、原子扣减、一次性回补 | 内存或隔离数据库库存账本 | SKU 库存表及原子 SQL |
| 支付 | 预支付、成功回调、关闭、退款、查询 | Mock 支付适配器 | 微信支付 V3 适配器 |
| 物流 | 发货、轨迹查询 | Mock 物流适配器 | 物流供应商适配器 |
| 首页与互动 | Banner、频道、收藏、足迹、评论 | 种子数据 | 内容/互动表 |

## 3. 业务规则要求

- 所有 Mock SKU 必须具备稳定的 ID、规格、售价、库存和上下架状态；不存在的商品或 SKU 必须返回业务错误，禁止兜底生成商品。
- 下单必须按当前商品快照重新校验价格与可售状态；订单明细写入不可变快照。
- 扣库存、取消/超时回补、退款回补均须幂等；重复请求和并发状态竞争不能多扣或多回补。
- Mock 支付必须走与真实支付相同的支付单、订单状态机、金额校验和订单日志路径。
- 各环境的提供方由配置决定，例如 `product.provider`、`inventory.provider`、`payment.provider`、`logistics.provider`；不得在业务代码中散落 `if (mock)`。

## 4. 环境规则

| 环境 | 允许的提供方 | 限制 |
| --- | --- | --- |
| local/dev | Mock 或真实数据源 | Mock 写操作仅允许经过登录态和开发开关 |
| test | Mock/隔离数据库 | 自动验收必须可重复执行并清理数据 |
| staging | 隔离的真实数据源或受控 Mock | 禁止匿名管理端操作 |
| prod | 数据库、微信支付、真实物流 | 强制禁用 Mock 支付、发货、退款等变更接口 |

## 5. 替换策略

1. 先冻结 API 响应与错误码，并为每个能力建立契约测试。
2. 在 Mock 提供方下让商品浏览、购物车、下单、支付、发货、售后全流程通过。
3. 先替换商品/SKU 与库存，交易自动验收不变。
4. 再替换首页/互动内容数据，最后替换支付与物流第三方实现。
5. 每次替换使用开关灰度，并在隔离环境跑同一组契约、集成和回归测试；通过后才移除对应 Mock 默认配置。

## 6. 非目标

- 不在本设计中直接接入微信商户资料或物流供应商。
- 不因提供方切换重写小程序页面。
- 不允许以“先 Mock”为理由延后鉴权、金额校验、状态机、库存幂等和订单日志。
