# 交易演示数据与可替换 Provider 设计

> 日期：2026-08-06  
> 状态：已确认  
> 目标：在没有真实客户数据和第三方账号的阶段，完整验证订单与售后后台；后续接入真实退款、物流时保持管理后台 API 和核心业务入口稳定。

## 1. 核心原则

1. 演示数据只存在于独立的 `sql/demo` 脚本，不进入生产初始化脚本。
2. Mock 只替代退款渠道和物流轨迹来源，订单、支付、库存、售后状态与操作日志仍写入数据库。
3. 管理后台继续使用现有订单、售后和物流 API，不感知 Provider 类型。
4. Provider 通过配置选择；开发环境使用 `mock`，生产环境默认 `disabled`，未配置真实实现时禁止伪造退款或物流结果。
5. 退款请求以售后单号作为稳定幂等标识，真实 Provider 必须保证重复调用不会重复退款。

## 2. Provider 契约

### 退款

- 输入：售后单号、订单号、支付单号、退款金额、退款原因。
- 输出：Provider 退款单号、处理状态（成功或处理中）、说明。
- Mock Provider 立即返回成功；真实 Provider 可返回处理中，并通过后续回调完成本地状态。
- Provider 调用失败时不得把支付单和订单标记为已退款。

### 物流

- 输入：订单 ID、物流公司、物流单号、发货时间、订单状态。
- 输出：按时间倒序的物流轨迹。
- Mock Provider 根据稳定输入生成可复现轨迹；生产默认 Disabled Provider 返回空轨迹，不伪造物流进度。

## 3. 售后数据规则

- 后台审批使用 `afterSaleId` 定位售后单，不以订单的“最新售后单”代替明确标识。
- 售后列表必须使用数据库分页，禁止全表加载后内存分页。
- 拒绝原因由前后端共同校验，长度为 4 至 200 个字符。
- 新增“退款处理中”状态，用于承载真实退款 Provider 的异步结果；Mock Provider 仍直接进入“已退款”。
- 退款渠道、渠道退款单号、退款说明和退款完成时间保存到售后单，便于后续对账。

## 4. 演示数据

- 固定生成多个演示用户和订单，覆盖待付款、待发货、待收货、已完成、已取消、待审核售后、退款处理中、已退款、已拒绝和已撤销。
- 订单、订单项、支付单、物流、售后和订单日志必须相互一致。
- 脚本可重复执行，只清理预留的演示 ID 区间，不影响手工创建或真实业务数据。

## 5. 配置与替换

```yaml
trade:
  refund:
    provider: mock
  logistics:
    provider: mock
```

生产环境默认值均为 `disabled`。后续接入真实渠道时，实现相同接口并将配置切换为真实 Provider 类型即可。

## 6. 本期边界

- 不接入真实微信退款凭证与物流供应商账号。
- 不实现退货地址、用户回寄物流和商家收货确认的完整退货链路。
- 不改变管理后台订单与售后页面的主导航和现有核心接口路径。
