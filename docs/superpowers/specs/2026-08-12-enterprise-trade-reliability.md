# 企业交易可靠性第二轮整改规格

> 日期：2026-08-12
> 范围：退款、售后时限、库存审计、批处理隔离与管理端接口约束

## 目标

1. 外部退款调用不得依赖一个尚未提交的本地事务状态。
2. 退款调用失败或服务重启后，系统必须能够从数据库任务继续重试和查单。
3. 售后期限必须使用独立的订单完成时间，不能被通用更新时间延长。
4. 后台库存调整必须记录真实管理员和调整原因。
5. 批量售后超时处理中的单条冲突不得回滚整批记录。
6. 管理端交易写接口必须使用明确的 HTTP 方法。

## 关键约束

- 售后批准只负责将售后单提交为“退款处理中”，该状态先独立提交。
- 渠道退款由独立服务执行；相同售后单号作为退款幂等号重复调用。
- 退款任务记录尝试次数、下次执行时间和最后错误，超过阈值后停止自动调用并保留人工同步入口。
- 用户确认收货和系统自动确认收货均写入 `finish_time`。
- 历史已完成订单迁移时使用现有更新时间回填一次，后续不再随订单更新漂移。
- 商品聚合保存只有在库存发生变化时要求填写调整原因。

## 验收

- 批准退款后，即使首次渠道调用异常，售后仍保持退款处理中并可由任务重试。
- 退款成功、处理中、明确失败三类结果均可幂等落库。
- 库存流水可定位管理员 ID，备注包含管理员填写的调整原因。
- 一条超时售后发生状态冲突时，其他售后仍能完成关闭。
- 后端单元测试、数据库迁移和管理后台构建通过。
