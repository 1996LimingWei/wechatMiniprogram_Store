# 微信小程序正式发布与生产可用规格

## 1. 目标

本规格将项目目标从“可演示的交易 MVP”提升为“可提交微信审核、可真实收款、可处理售后、可持续运营”的正式微信小程序。

完成标准不是页面能够打开或成功路径能够跑通，而是：

1. 不存在匿名管理、伪造支付、重复扣款、超卖、越权读写等高风险问题。
2. 用户身份、隐私信息、订单、支付、库存、退款和课程权益具备完整且可审计的一致性。
3. 小程序配置、域名、类目、资质、隐私保护指引和商品文案满足微信发布要求。
4. 异常、超时、重复通知、服务重启和依赖故障均有自动或人工兜底。
5. 正式环境只使用真实数据，不暴露开发 Mock、测试按钮、空白页面或“开发中”入口。

## 3. 发布门禁

### 3.1 主体、类目与资质

1. 小程序主体、名称、头像、简介、服务类目和实际经营内容必须一致。
2. 食品、保健食品、药品、医疗器械、教育课程、视频内容分别核对所需类目和资质。
3. 没有相应经营资质的商品不得上架，不得通过模糊分类绕过审核。
4. 商品标题、详情、推荐语不得包含未经证明的治疗、预防疾病或绝对化功效表达。
5. 隐私保护指引中申报的个人信息类型、使用目的和代码实际行为必须一致。
6. 完成小程序备案、服务器域名备案、客服和投诉处理信息配置。

### 3.2 环境与配置

1. 开发、测试、生产环境必须分离；正式包不得指向 localhost、HTTP 地址或测试数据库。
2. 生产请求、上传、下载和 WebSocket 域名必须使用 HTTPS，并配置到微信公众平台合法域名。
3. AppID、AppSecret、商户号、APIv3 密钥、商户私钥和证书不得进入前端包或 Git 仓库。
4. 生产环境必须关闭 Mock 登录、Mock 支付、模拟发货、模拟退款和所有测试数据接口。
5. 第三方图片、视频和文件必须迁移到自有或已授权的稳定对象存储/CDN 域名。

### 3.3 身份、权限与隐私

1. `wx.login` 的 code 只能由后端换取 OpenID/session_key；session_key 不得返回客户端或写入日志。
2. 公开接口采用明确白名单；购物车、地址、订单、支付、收藏、足迹和评价写入必须认证。
3. `/admin-api/**` 必须使用独立管理员身份、角色权限和操作审计，未完成前默认拒绝访问。
4. 所有资源访问必须校验数据归属，不能仅依赖前端传入的 userId。
5. 登录前展示用户协议与隐私政策；需要隐私接口时按微信隐私授权流程获取同意。
6. 提供账号注销、数据删除申请、地址删除、足迹清理和登录态失效能力。
7. 手机号、地址、OpenID、session_key 等敏感数据最小化采集，展示脱敏，存储加密或受控，日志禁止明文输出。

### 3.4 商品、定价与库存

1. 下单必须使用真实 SPU/SKU，不允许回退 Mock 商品或合成 SKU。
2. 服务端是价格和优惠的唯一权威；提交订单时重新校验商品状态、SKU、库存和价格。
3. 报价需要记录原价、会员优惠、活动优惠、优惠券、运费、应付和实付，并按订单明细分摊。
4. 库存采用 SKU 维度的预占、支付确认、取消释放和退款/退货处理规则。
5. 所有库存变化写入不可变流水，支持按订单对账和人工修正。
6. 数量、金额和分页参数必须设置上下限，金额统一使用整数分或长整型计算。

### 3.5 订单、支付与退款

1. 订单提交使用客户端请求号和数据库唯一约束实现幂等。
2. 订单、支付、履约、售后分别建模，通过显式状态机控制合法流转。
3. 微信支付使用 APIv3，小程序端只负责调起支付；最终支付结果以后端验签回调或主动查单为准。
4. 支付通知需要验签、解密、金额/商户号/AppID 校验、通知去重和完整原始通知审计。
5. 商户订单号在商户号内唯一；订单超时后同时关闭本地订单和微信支付订单。
6. 退款使用独立退款单，处理退款回调、重复通知、失败重试和主动查询。
7. 建立支付、退款、订单、库存的定时对账与人工补偿工作台。

### 3.6 履约、售后与课程

1. 实物和虚拟商品必须区分履约类型；混合购物车按履约规则拆单。
2. 实物订单处理地址、运费、发货、物流、自动收货和售后期限。
3. 课程订单不要求地址和运费；支付成功后可靠且幂等地生成课程权益。
4. 课程权益生成失败必须自动重试，并提供人工补发和审计记录。
5. 售后支持订单明细、数量、退款金额、凭证、退货物流、商家收货、拒绝理由和退款流水。
6. 售后状态不能覆盖订单主状态，部分退款和多次售后必须可表达。

### 3.7 小程序体验与性能

1. 移除空白页面、不可用入口、开发中提示和正式环境测试按钮。
2. 网络请求统一处理超时、重试边界、401 刷新并发、错误文案和 loading 引用计数。
3. 提交订单和支付操作必须防重复点击；支付取消、处理中、成功和失败均有明确恢复路径。
4. 页面列表具备加载中、空状态、失败重试和分页结束状态。
5. 配置 `sitemap.json`、版本更新、弱网提示、分享路径校验和页面参数校验。
6. 控制主包体积，按业务分包；图片使用合适尺寸、懒加载、压缩和 CDN。
7. 关键页面在常见 iOS/Android 微信版本、不同屏幕、安全区域和弱网下完成真机验证。

### 3.8 运维与质量

1. 提供健康检查、就绪检查、结构化日志、请求 ID、订单号和支付单号关联。
2. 监控登录、下单、支付回调、退款、库存失败率、任务积压和接口延迟，并配置告警。
3. 数据库迁移可重复、可验证、可备份和可回滚；生产启动不得自动覆盖业务数据。
4. 定时任务具备多实例互斥、批处理上限、失败重试和指标。
5. 自动化测试覆盖权限、越权、金额、库存、幂等、状态竞争、重复通知、退款和课程权益。
6. CI 必须执行编译、单元测试、集成测试、迁移测试、静态扫描和小程序构建检查。

## 4. 外部资料阻断项

以下资料无法通过代码生成，缺失时不得宣称可以正式上线：

1. 微信小程序主体、已备案 AppID 和服务类目。
2. 食品/保健食品/药品/医疗器械/课程视频对应经营资质。
3. 已备案 HTTPS API 域名、对象存储/CDN 域名及证书。
4. 微信支付商户号、AppID 绑定关系、APIv3 密钥、商户私钥/证书或微信支付公钥。
5. 正式隐私保护指引、用户协议、经营主体、客服、退换货和投诉信息。
6. 真实商品、SKU、库存、物流模板、售后规则和课程内容版权资料。

## 5. 验收结论

只有发布门禁全部通过、自动化门禁无失败、外部资料齐全，并完成微信开发者工具体验评分和真机回归后，项目状态才允许标记为“可提审”；完成微信审核和真实小额支付/退款验证后，才允许标记为“可上线”。
