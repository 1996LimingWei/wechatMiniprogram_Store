# 服务器部署与小程序更新操作教程

> 适用项目：陕铺 v1.0（`shop-backend` / `shop-admin` / `shop-miniapp`）
> 编写日期：2026-11-24
> 适用场景：测试期预演部署、后续版本迭代、微信小程序体验版发布
> 部署根目录：`/www/shop`

本文分两条路线：

- **路线 A：预演部署（当前阶段）**：团队测试还没结束时，用 `catalog` 模式先把服务跑起来，熟悉流程。不接支付、不接物流，不把这次结果当作正式交付证据。
- **路线 B：正式交付部署（测试完成后）**：使用固定镜像包、加密备份和 `commerce` 模式，按发布手册留下可追溯记录。

两条路线的服务器初始化、域名、证书、小程序发布步骤相同，差别在部署命令和交付要求。

## 2. 服务器初始化（只做一次）

### 2.1 宝塔面板安全

1. 修改默认面板端口（如果仍是 `8888`）。
2. 开启系统防火墙，只放行 22、80、443、面板端口。
3. 关闭 Ping、配置告警通知。
4. 腾讯云控制台的防火墙也要放行同样的端口，两层缺一不可。

### 2.2 释放 80/443 端口

当前 Compose 里的 `nginx` 容器要占用宿主机的 80/443。宝塔自带的 Nginx 如果还在监听，会报 `Bind for 0.0.0.0:80 failed`。

先做只读盘点，确认没有客户其他站点：

```bash
ls -1 /www/server/panel/vhost/nginx/ 2>/dev/null
grep -R "^ *server_name" /www/server/panel/vhost/nginx/ 2>/dev/null
```

本服务器目前只有占位站点时，按下面处理：

1. **（可选）** 宝塔 → **网站** → 删除之前建的占位站点（确认没有客户其他站点）。不删也可以，它只是占位配置，关键是下一步停掉 Nginx。
2. 宝塔 → **软件商店** → 找到 **Nginx** → **停止**，并设置为不自动启动。
3. 回到终端确认端口已释放：

```bash
ss -lntp | grep -E ':(80|443)\b'
```

没有输出才继续。**如果服务器上还有客户的其他网站，不要执行停止 Nginx**，需要改为“宝塔 Nginx 反代到 Docker 的 8080/8443”，这需要额外的 Compose 端口覆盖和宝塔反代配置，属于另一套适配方案，先找技术负责人确认。

> 宝塔里的 `bhtjl.top` 站点只是之前建的占位配置，根目录 `/www/wwwroot/bhtjl.top` 不是商城程序。真正的管理后台和小程序 API 由 Docker 的 `admin` / `backend` / `nginx` 容器提供。删除站点记录不会删除域名、DNS、`/www/shop` 代码或 Docker 数据；不想删就保留，但 Nginx 一定要停。

> 宝塔面板本身不依赖 Nginx，停止 Nginx 后面板仍可正常访问。证书也不用宝塔申请，直接使用客户提供的证书文件。

### 2.3 安装 Docker 与 Compose

本服务器是 OpenCloudOS（腾讯云），优先用宝塔左侧「Docker」模块安装，面板会按系统适配。`get.docker.com` 脚本对 OpenCloudOS 不一定识别，失败时不要反复重试。

**方式一：宝塔左侧「Docker」菜单（推荐）**

1. 宝塔左侧菜单 → **Docker** → 按页面提示安装 Docker。
2. 终端验证：

```bash
docker --version
docker compose version
systemctl is-enabled docker
```

**方式二：面板模块不可用时，用 dnf 安装（OpenCloudOS / CentOS / RHEL 系）**

```bash
dnf install -y dnf-utils device-mapper-persistent-data lvm2
dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
dnf install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
systemctl enable --now docker
docker --version
docker compose version
```

> Debian/Ubuntu 才使用 `curl -fsSL https://get.docker.com | sh`。
> 如果 dnf 报 404 或找不到包，说明当前系统的 `$releasever` 不被 Docker 仓库识别，回到宝塔「Docker」模块安装，不要继续硬装。

能输出版本号即可。国内服务器如果拉取镜像慢，可在 `/etc/docker/daemon.json` 配置当前可用的镜像加速地址；不确定镜像源是否有效时，先不要乱配，避免 Docker 起不来。

同时限制 Docker 日志大小，防止磁盘被日志占满：

```bash
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}
EOF
systemctl restart docker
```

> 如果之前已经配置过镜像加速，把 `log-driver` 两行合并进原文件，不要覆盖掉原有配置。

### 2.4 内存不足时增加 Swap

内存 2GB 的轻量服务器建议总 Swap 至少 2GB；如果还要在这台机器上构建镜像，建议加到 4GB 以上，否则 MySQL + Java + Maven 测试容易 OOM：

```bash
free -h
fallocate -l 2G /swapfile || dd if=/dev/zero of=/swapfile bs=1M count=2048
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
grep -q '^/swapfile' /etc/fstab || echo '/swapfile none swap sw 0 0' >> /etc/fstab
free -h
```

> 如果已经存在 `/swapfile`，不要重复执行上面的 `fallocate`，改为追加一个 `/swapfile2`：

```bash
fallocate -l 4G /swapfile2 || dd if=/dev/zero of=/swapfile2 bs=1M count=4096
chmod 600 /swapfile2
mkswap /swapfile2
swapon /swapfile2
grep -q '^/swapfile2' /etc/fstab || echo '/swapfile2 none swap sw 0 0' >> /etc/fstab
free -h
```

`scripts/` 下的数据库初始化和发布工具需要 Python 3.10+：

```bash

.venv-delivery/bin/pip install -r scripts/requirements-delivery.txt
```

## 3. 上传代码与准备目录

### 3.1 拉取固定版本

```bash
cd /www
git clone <仓库地址> shop
cd /www/shop
git checkout <要部署的分支或 tag>
git rev-parse HEAD
```

把 `git rev-parse HEAD` 的输出记到发布记录里。**不要直接部署未提交的本地修改**，否则出问题无法复现。

私有仓库可以用部署密钥，或者在宝塔文件管理器上传压缩包后解压，但后续更新仍建议走 Git。

### 3.2 创建运行目录

```bash
cd /www/shop
mkdir -p deploy/secrets/tls \
         deploy/secrets/wechat-pay \
         deploy/data/mysql \
         deploy/data/redis \
         deploy/data/material \
         deploy/logs/backend \
         deploy/logs/nginx \
         deploy/backups/mysql
chmod 700 deploy/secrets
```

这些目录都在 `.gitignore` 中，不会被提交。

### 3.3 放置证书

把客户提供的证书上传到：

- `deploy/secrets/tls/fullchain.pem`（证书链）
- `deploy/secrets/tls/privkey.pem`（私钥）

如果客户给的文件名不同，按用途改名即可：证书链/站点证书 → `fullchain.pem`，私钥 → `privkey.pem`。如果证书是“叶证书 + CA”两个文件，把叶证书放前面、CA 放后面拼接成 `fullchain.pem`，顺序不能反。

```bash
chmod 600 deploy/secrets/tls/fullchain.pem deploy/secrets/tls/privkey.pem
```

检查证书域名、有效期和配对关系：

```bash
openssl x509 -in deploy/secrets/tls/fullchain.pem -noout -subject -dates -ext subjectAltName
openssl x509 -in deploy/secrets/tls/fullchain.pem -noout -pubkey | openssl sha256
openssl pkey -in deploy/secrets/tls/privkey.pem -pubout | openssl sha256
```

两个 SHA256 必须一致。证书到期前要提前续期，替换文件后重启 Nginx 容器：

```bash
shopcompose restart nginx
```

## 4. 生成生产配置 `.env.prod`

### 4.1 用工具生成，不要手抄密码

```bash
cd /www/shop
.venv-delivery/bin/python scripts/configure_delivery.py --domain bhtjl.top
chmod 600 .env.prod
```

该命令会：

- 以 `shop.example.com` 模板生成 `bhtjl.top` 的配置；
- 自动生成数据库 root、应用数据库用户、Redis 的独立随机密码；
- 默认 `APP_DELIVERY_MODE=catalog`、`WECHAT_PAY_ENABLED=false`；
- 追加 `DELIVERY_ADMIN_PASSWORD`（初始管理员密码）和备份密码。

**禁止覆盖已有 `.env.prod`**。文件已存在时脚本会拒绝执行，这是保护数据库密码不被重置。

### 4.2 检查并补充配置

```bash
vi .env.prod
```

逐项确认：

| 配置项 | 当前阶段填法 |
|--------|-------------|
| `APP_DELIVERY_MODE` | `catalog`（只做商品录入与浏览，不接支付） |
| `APP_DOMAIN` | `bhtjl.top` |
| `APP_EXTERNAL_BASE_URL` | `https://bhtjl.top` |
| `WEB_CORS_ALLOWED_ORIGIN_PATTERNS` | `https://bhtjl.top` |
| `MYSQL_DATABASE` | `shop` |
| `MYSQL_USER` / `MYSQL_PASSWORD` | 工具已生成，**首次初始化后不要再改** |
| `MYSQL_ROOT_PASSWORD` | 工具已生成，妥善保存 |
| `REDIS_PASSWORD` | 工具已生成 |
| `WX_MA_APPID` | 小程序真实 AppID，例如 `wx34175bfa441e4316`（以客户账号为准） |
| `WX_MA_SECRET` | 小程序真实 AppSecret；不测试登录可暂时留空 |
| `WECHAT_PAY_*` | 当前阶段保持 `WECHAT_PAY_ENABLED=false`，其余占位值不动 |
| `TRADE_LOGISTICS_PROVIDER` | 当前阶段保持 `kuaidi100` 占位即可，不测试物流不影响启动 |
| `MATERIAL_PUBLIC_BASE_URL` | `https://bhtjl.top/uploads/material/` |
| `DELIVERY_ADMIN_PASSWORD` | 初始管理员密码，至少 16 字符，工具已生成 |

关于小程序登录：

- 只浏览商品：`WX_MA_APPID`/`WX_MA_SECRET` 不填也能启动，但点“微信登录”会失败。
- 要测试登录：必须填真实 AppID 和 AppSecret，且 `WX_MA_APPID` 与小程序 `manifest.json`、`project.config.json` 中的 AppID 一致。

查看初始管理员密码：

```bash
grep '^DELIVERY_ADMIN_PASSWORD=' .env.prod
```

### 4.3 发布前静态预检

```bash
shopcompose config --quiet
.venv-delivery/bin/python scripts/release_preflight.py --env .env.prod
.venv-delivery/bin/python scripts/generate_migration_manifest.py --check
```

- `config --quiet` 通过，说明 Compose 能正确解析 `.env.prod`，没有缺失的必填变量。
- `release_preflight.py` 通过，说明必填项、密码长度、HTTPS 地址格式都合格。
- `generate_migration_manifest.py --check` 通过，说明 `sql/migrations` 与发布迁移清单一致。
- 如果清单检查失败：说明团队新增或修改了迁移 SQL，先执行不带 `--check` 的命令生成清单，审查差异并提交后再部署：

```bash
.venv-delivery/bin/python scripts/generate_migration_manifest.py
git diff -- shop-backend/shop-server/src/main/resources/delivery-migrations.properties
```

## 5. 首次部署（路线 A：预演）

> 第一次部署必须是空数据库。`prepare_database.py initialize` 只接受空库，失败后不会自动清空重试。

### 5.1 构建镜像

先确认 Dockerfile 已启用仓库里的 Maven 镜像配置：

```bash
cd /www/shop
grep -n 'COPY .mvn/settings.xml /root/.m2/settings.xml' shop-backend/Dockerfile
```

没有输出时，在 `shop-backend/Dockerfile` 的 `WORKDIR /app` 下面补一行：

```dockerfile
COPY .mvn/settings.xml /root/.m2/settings.xml
```

然后分开构建。推荐用 `nohup` 放后台，避免终端断开影响构建：

```bash
cd /www/shop
alias shopcompose='docker compose --env-file .env.prod -f docker-compose.prod.yml'

nohup docker compose --env-file .env.prod -f docker-compose.prod.yml build --progress plain backend \
  > build-backend.log 2>&1 &
tail -f build-backend.log
```

看到 `Image shanpu/backend:local Built` 后按 `Ctrl+C` 退出日志查看，**这不会停止构建**。再构建管理后台：

```bash
nohup docker compose --env-file .env.prod -f docker-compose.prod.yml build --progress plain admin \
  > build-admin.log 2>&1 &
tail -f build-admin.log
```

两次分开构建，不要写成 `build backend admin`。后端 Dockerfile 里是 `mvn package -B`，会跑测试，2GB 内存的服务器同时构建两个镜像很容易 OOM。首次构建会下载 Maven、Node 依赖，可能需要 10～30 分钟。构建失败先看网络和磁盘空间：

```bash
df -h
docker system df
```

### 5.2 先启动数据库与 Redis

```bash
shopcompose up -d mysql redis
shopcompose ps
```

看到 `mysql`、`redis` 都是 `healthy` 再继续。

### 5.3 初始化数据库

先把初始管理员密码注入环境变量，工具只从环境读取，不写入命令行参数：

```bash
export DELIVERY_ADMIN_PASSWORD="$(grep -E '^DELIVERY_ADMIN_PASSWORD=' .env.prod | cut -d= -f2-)"
.venv-delivery/bin/python scripts/prepare_database.py initialize --env .env.prod --database shop
unset DELIVERY_ADMIN_PASSWORD
```

这一步会：

- 执行 `sql/init.sql`；
- 按顺序执行全部 `sql/migrations/V*__*.sql`；
- 写入 `schema_migration_history` 校验和；
- 清理演示业务数据；
- 把 `admin` 的密码设置成 `DELIVERY_ADMIN_PASSWORD`。

> 如果提示“初始化仅允许空库”，说明库里已经有表。预演阶段确认数据可丢弃后，才可以换一个新的数据库名重新来；**客户正式环境禁止删库重试**。

### 5.4 修正素材与日志目录属主

后端容器以 UID `10001` 运行，宿主机目录需要可写：

```bash
shopcompose run --rm --no-deps --user 0 --entrypoint sh backend \
  -c 'chown -R 10001:10001 /app/material /app/logs'
```

### 5.5 启动全部服务

```bash
shopcompose up -d --wait --wait-timeout 300
shopcompose ps
```

期望结果：

- `mysql`、`redis`、`backend` 为 `healthy`；
- `admin`、`nginx` 为 `running`；
- 没有容器反复重启。

### 5.6 验证

```bash
curl -fsS https://bhtjl.top/healthz
curl -fsS https://bhtjl.top/readyz
```

- `/healthz` 返回 `ok`，说明 Nginx 正常。
- `/readyz` 返回 `{"status":"UP"}`，说明后端和数据库都正常。

如果 DNS 还没生效，可以指定解析地址验证：

```bash
curl -fsS --resolve bhtjl.top:443:127.0.0.1 https://bhtjl.top/readyz
```

### 5.7 登录后台做冒烟测试

1. 浏览器打开 `https://bhtjl.top/`。
2. 账号 `admin`，密码为 `.env.prod` 中的 `DELIVERY_ADMIN_PASSWORD`。
3. 进入后立即修改管理员密码。
4. 修改成功后，可以删除 `.env.prod` 中的 `DELIVERY_ADMIN_PASSWORD` 一行（正式环境按发布手册要求删除）。
5. 上传一张商品图片，确认 `https://bhtjl.top/uploads/material/...` 能打开。
6. 新建一个分类和一个商品，确认小程序端能读到（小程序步骤见第 8 节）。

把以下信息记到你的发布记录（不要写密码）：

## 6. 正式交付部署（路线 B：测试完成后）

预演通过、团队测试完成、客户资料齐全后，正式交付按 `docs/deployment/2026-11-04-release-runbook.md` 执行。核心差别：

1. 代码必须已提交，`git status --porcelain` 无输出。
2. 在构建机（与服务器同 CPU 架构）封存一次镜像包，服务器不再现场构建。以下命令在构建机的仓库根目录执行，Python 环境按 2.5 节准备：

```bash
.venv-delivery/bin/python scripts/release_images.py --env .env.prod --output deploy/releases/candidate-<commit>
```

3. 把整个 `candidate-<commit>` 目录传到服务器 `deploy/releases/`，校验 SHA256 后在服务器执行：

```bash
# 首次
.venv-delivery/bin/python scripts/deploy_release.py initialize \
  --env .env.prod --bundle deploy/releases/candidate-<commit>

# 后续升级（必须有停写备份和独立挂载存储）
.venv-delivery/bin/python scripts/deploy_release.py upgrade \
  --env .env.prod \
  --bundle deploy/releases/candidate-<commit> \
  --backup deploy/backups/before-<版本>.zip \
  --offsite-dir /mnt/shanpu-backup
```

`upgrade` 的 `--offsite-dir` 必须是真实的独立挂载目录，不能用本机普通目录冒充异机备份。正式交付前需要先准备这个存储和告警接收人。

4. 开放交易时，把 `.env.prod` 改为 `APP_DELIVERY_MODE=commerce`、`WECHAT_PAY_ENABLED=true`，补齐微信支付、快递 100 信息，重新预检并发布。切换前先看 `docs/deployment/2026-11-04-release-runbook.md` 第 7 节。

> 如果路线 A 已经初始化了同一个 `shop` 库，后续不要再执行 `initialize`（只接受空库）。预演数据要继续用时，走 `upgrade` 流程；不想保留预演数据时，在正式环境使用新库或新服务器重新初始化。预演录入的商品数据不能自动视为正式交付数据。

> 路线 A 的目标是“跑起来、熟悉流程”。正式交付的镜像包、备份、验收记录不能用路线 A 的结果代替。

## 7. 日常更新后端与管理后台

> 适用：团队提交了新代码，需要更新服务器。小程序更新见第 8、9 节。

### 7.0 先确认代码是怎么上传的

`3.1` 的 `git clone` 只用于第一次部署。`/www/shop` 已经有代码时，不要重复 clone，先盘点：

```bash
ls -ld /www/shop
cd /www/shop && git rev-parse --is-inside-work-tree 2>/dev/null || echo "NOT_A_GIT_REPO"
cd /www/shop && git remote -v 2>/dev/null
cd /www/shop && git log -1 --oneline 2>/dev/null
ls -l /www/shop/.env.prod 2>/dev/null || echo "NO .env.prod"
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

- 能输出 commit：是 Git 仓库，按 7.1 更新。
- 输出 `NOT_A_GIT_REPO`：当时是 ZIP/SFTP 上传的，`git pull` 用不了，按 7.7 更新。
- 输出 `NO .env.prod`：第 4 节还没做，先补配置再更新。

### 7.1 更新前：确认版本并备份

```bash
cd /www/shop
git fetch --all
git checkout <部署分支>
git pull
git rev-parse HEAD
```

备份数据库（预演阶段使用；正式环境使用发布工具的加密备份）：

```bash
mkdir -p deploy/backups/mysql
shopcompose exec -T mysql sh -c \
  'export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"; exec mysqldump -uroot --single-transaction --routines --triggers --default-character-set=utf8mb4 "$MYSQL_DATABASE"' \
  > "deploy/backups/mysql/manual-$(date +%Y%m%d-%H%M).sql"
ls -lh deploy/backups/mysql/
```

给当前镜像打快照，方便回滚（如果 `.env.prod` 自定义过 `SHOP_BACKEND_IMAGE`/`SHOP_ADMIN_IMAGE`，按实际镜像名替换）：

```bash
TAG=$(date +%Y%m%d-%H%M)
docker tag shanpu/backend:local shanpu/backend:$TAG
docker tag shanpu/admin:local shanpu/admin:$TAG
echo $TAG
```

### 7.2 构建新镜像

```bash
shopcompose build backend
shopcompose build admin
```

低内存服务器必须分开构建，原因见 5.1。

### 7.3 如果本次包含数据库迁移

先停后端，执行迁移，再启动：

```bash
shopcompose stop backend
.venv-delivery/bin/python scripts/prepare_database.py migrate --env .env.prod --database shop
shopcompose up -d --wait --wait-timeout 300
```

如果没有新迁移，跳过 `stop`/`migrate`，直接：

```bash
shopcompose up -d --wait --wait-timeout 300
```

迁移失败时后端会保持停止状态，这是有意的保护。先看报错和数据库现场，确认原因后再重试，不要直接反复启动。

### 7.4 更新后验证

```bash
shopcompose ps
curl -fsS https://bhtjl.top/readyz
shopcompose logs --tail=100 backend
```

再登录后台，检查商品、订单、库存等本次改动涉及的页面。

### 7.5 回滚应用

只回滚应用、保留当前数据库：

1. 编辑 `.env.prod`，指向第 7.1 步打出的镜像 tag：

```env
SHOP_BACKEND_IMAGE=shanpu/backend:20261124-1530
SHOP_ADMIN_IMAGE=shanpu/admin:20261124-1530
```

2. 启动：

```bash
shopcompose up -d --no-build backend admin
curl -fsS https://bhtjl.top/readyz
```

3. 验证完成后，把 `.env.prod` 中的两行改回 `shanpu/backend:local` / `shanpu/admin:local`。

> 如果本次迁移改坏了数据结构，只回滚镜像不够。正式环境必须先在隔离库演练恢复，不能直接拿旧备份覆盖线上新增订单。

### 7.6 常用排障命令

```bash
shopcompose ps
shopcompose logs -f --tail=200 backend
shopcompose logs -f --tail=200 nginx
docker stats --no-stream
df -h
```

### 7.7 ZIP 上传方式的迭代

如果 `/www/shop` 不是 Git 仓库，不要为了更新删掉整个目录：`.env.prod`、`deploy/secrets/`、`deploy/data/` 都在里面，删了数据库和证书就没了。

本地打包时排除运行数据与构建产物：

```bash
cd /path/to/wechatMiniprogram_Store
zip -r shop-update.zip . \
  -x '.git/*' '*/node_modules/*' 'shop-admin/dist/*' \
     'shop-miniapp/unpackage/*' '*/target/*' '.venv-delivery/*' \
     'deploy/data/*' 'deploy/secrets/*' 'deploy/logs/*' \
     'deploy/backups/*' '.env.prod'
```

上传到 `/www` 后覆盖解压并重建：

```bash
cd /www/shop
unzip -o /www/shop-update.zip
shopcompose build backend admin
shopcompose up -d --wait --wait-timeout 300
curl -fsS https://bhtjl.top/readyz
```

> ZIP 覆盖不会删除服务端已移除的旧文件，也不会让 `release_images.py` / `deploy_release.py` 的 `git status` 检查通过。预演阶段可以用；正式交付前建议改成 Git 仓库，或在本地用 `git bundle` 把历史带到服务器。

## 8. 小程序体验版发布（第一次）

> 本节在**开发机**执行，不在 Linux 服务器执行。小程序构建依赖 HBuilderX。

### 8.1 微信平台一次性配置

登录 [微信公众平台](https://mp.weixin.qq.com)：

| 位置 | 操作 |
|------|------|
| 开发管理 → 开发设置 → 服务器域名 | request、uploadFile、downloadFile 合法域名都填 `https://bhtjl.top` |
| 开发管理 → 开发设置 → 开发者ID | 确认 AppID，生成/重置 AppSecret |
| 设置 → 基本设置 | 确认小程序名称、头像、服务类目、简介（客户主体） |
| 设置 → 服务内容声明 | 按项目收集的字段配置用户隐私保护指引 |
| 管理 → 成员管理 | 添加体验成员（测试人员微信号） |
| 设置 → 基本设置 → 小程序备案 | 完成小程序备案（正式发布必需，建议体验版阶段一并完成） |

注意：

- 域名必须已备案，且必须是 HTTPS。
- 开发者工具里的“不校验合法域名”只对模拟器有效，真机体验版仍会校验，所以域名白名单必须配置。
- 客服功能需要在微信后台开通，`open-type="contact"` 才能进入会话。

### 8.2 确认小程序 AppID

以下三处必须一致：

- `shop-miniapp/manifest.json` → `mp-weixin.appid`
- `shop-miniapp/project.config.json` → `appid`
- 微信公众平台当前小程序的 AppID

当前仓库中的值是 `wx34175bfa441e4316`。如果这是历史测试 AppID，上传前必须改成客户正式 AppID，并确认你的微信号是该小程序的开发者。

### 8.3 构建体验版（推荐用脚本）

在仓库根目录执行：

```bash
cd /path/to/wechatMiniprogram_Store

python3 scripts/build_miniapp_release.py \
  --cli /Applications/HBuilderX.app/Contents/MacOS/cli \
  --api-root https://bhtjl.top/ \
  --environment staging
```

参数说明：

- `--cli`：HBuilderX 的 CLI 路径。macOS 默认在 `/Applications/HBuilderX.app/Contents/MacOS/cli`；Windows 一般是 `HBuilderX安装目录\cli.exe`。
- `--api-root`：必须是 HTTPS 域名根地址，不能带 `/app-api/`、账号密码或查询参数。
- `--environment staging`：生成体验版构建，强制 HTTPS 校验。

脚本会自动：

1. 临时写入 `shop-miniapp/config/build-target.js`；
2. 调用 HBuilderX 发行编译到 `shop-miniapp/unpackage/dist/build/mp-weixin`；
3. 检查产物里确实包含目标 API；
4. 写 `deploy/reviews/miniapp-release.json` 记录；
5. 恢复 `build-target.js` 原内容。

检查产物：

```bash
ls -la shop-miniapp/unpackage/dist/build/mp-weixin
cat deploy/reviews/miniapp-release.json
```

**GUI 备选方案**（不使用 CLI 时）：

1. 先把 `shop-miniapp/config/build-target.js` 改成：

```js
module.exports = { appEnv: 'staging', apiBaseUrl: 'https://bhtjl.top/' };
```

2. HBuilderX → 发行 → 小程序-微信，编译到 `shop-miniapp/unpackage/dist/build/mp-weixin`。
3. 上传后恢复文件，避免误提交：

```bash
git checkout -- shop-miniapp/config/build-target.js
```

### 8.4 上传体验版

先打开微信开发者工具并登录，确认：

- 设置 → 安全设置 → 服务端口已开启；
- 当前登录账号是该小程序的开发者。

```bash
/Applications/wechatwebdevtools.app/Contents/MacOS/cli upload \
```

也可以手动上传：微信开发者工具 → 导入项目（选择上面的 `mp-weixin` 目录）→ 点击“上传” → 填写版本号和备注。

上传成功后，回到微信公众平台：

1. 管理 → 版本管理 → 开发版本，找到刚上传的版本。
2. 点击“选为体验版”。
3. 生成体验版二维码，发给体验成员。
4. 管理 → 成员管理，确认体验成员已添加。

### 8.5 真机体验版验证清单

至少验证：

- [ ] 首页能加载
- [ ] 分类能切换
- [ ] 商品详情能打开
- [ ] 搜索能用

## 9. 后续小程序迭代流程

团队每次修改小程序后，按下面顺序走：

```text
改代码 → 本地开发自测 → 提升版本号 → 构建 staging → 上传开发版
      → 选为体验版 → 真机回归 → 构建 production → 上传 → 提交审核 → 发布
```

### 9.1 提升版本号

修改 `shop-miniapp/manifest.json`：

```json
{
  "versionName": "1.0.1",
  "versionCode": 4
}
```

`versionCode` 每次上传递增，避免覆盖或缓存问题。上传时的 `--version` 与 `versionName` 保持一致。

### 9.2 构建并上传体验版

```bash
python3 scripts/build_miniapp_release.py \
  --cli /Applications/HBuilderX.app/Contents/MacOS/cli \
  --api-root https://bhtjl.top/ \
  --environment staging

/Applications/wechatwebdevtools.app/Contents/MacOS/cli upload \
  --project "$(pwd)/shop-miniapp/unpackage/dist/build/mp-weixin" \
  --version 1.0.1 \
  --desc "体验版-20261125-修复商品详情"
```

### 9.3 构建正式版并提审

体验版验证通过后，用生产环境重新构建，**不要直接把体验版包提审**：

```bash
python3 scripts/build_miniapp_release.py \
  --cli /Applications/HBuilderX.app/Contents/MacOS/cli \
  --api-root https://bhtjl.top/ \
  --environment production

/Applications/wechatwebdevtools.app/Contents/MacOS/cli upload \
  --project "$(pwd)/shop-miniapp/unpackage/dist/build/mp-weixin" \
  --version 1.0.1 \
  --desc "正式版-20261125"
```

然后在微信公众平台：

1. 版本管理 → 开发版本 → 提交审核。
2. 按页面提示补齐类目、资质、隐私、测试账号等材料。
3. 审核通过后点击“发布”。
4. 发布后用正式版再做一次核心链路验证。

> 提审前先确认后端交付模式与小程序功能一致：服务器仍是 `catalog` 时，不要提交包含支付功能的版本；要开放支付，先按第 6 节切换为 `commerce` 并完成真实支付联调。

> 提审的包必须和体验版验证过的代码一致。上传后如果又改了代码，要重新构建、重新上传，不能拿旧包提审。

### 9.4 哪些情况必须重新提审

- 页面、文案、功能、接口地址有变化；
- 新增收集用户信息的字段；
- 新增支付、物流、客服等能力；
- 更换 AppID 或主体。

只改后端数据（商品、价格、库存、Banner）不需要重新提审。

## 10. 常见问题

### 10.1 启动时报 80/443 被占用

```bash
ss -lntp | grep -E ':(80|443)\b'
```

宝塔 Nginx 还在监听。按 2.2 停止 Nginx，或与负责人确认改用反代方案。

### 10.2 打开域名显示 502

后端没起来或数据库没连上：

```bash
shopcompose ps
shopcompose logs --tail=200 backend
curl -fsS https://bhtjl.top/readyz
```

常见原因：数据库没初始化、`.env.prod` 密码被改过、迁移没执行。

### 10.3 浏览器提示证书无效

- 确认 `fullchain.pem` 是完整证书链，不是只有叶证书；
- 确认 `privkey.pem` 与证书配对；
- 确认证书覆盖当前访问的域名（`bhtjl.top` 与 `www.bhtjl.top`）；
- 确认系统时间正确。

### 10.4 小程序请求失败

按顺序排查：

1. 微信后台服务器域名是否填了 `https://bhtjl.top`；
2. 域名是否备案；
3. 证书是否有效、是否为完整链；
4. 真机是否能打开 `https://bhtjl.top/readyz`；
5. 构建产物是否用的 `https://bhtjl.top/`，而不是 `127.0.0.1`。

### 10.5 小程序登录失败

- `WX_MA_APPID` 必须与小程序 AppID 一致；
- `WX_MA_SECRET` 必须是当前有效值；
- 微信后台的 AppSecret 重置后，服务器 `.env.prod` 要同步更新并重启后端：

```bash
shopcompose up -d backend
```

### 10.6 上传图片失败或 413

项目默认单文件上限 5MB，Nginx 上限 20MB：

- 压缩图片后再传；
- 确认 `MATERIAL_MAX_SIZE` 未被改小；
- 确认 `deploy/data/material` 属主为 `10001`。

### 10.7 磁盘满了

```bash
df -h
docker system df
docker image prune -f
```

`docker image prune` 只清理悬空镜像；确认没有回滚需求后再清理旧镜像和构建缓存。

### 10.8 数据库初始化失败后想重来

预演阶段、确认数据可丢弃时，才可以换新库名或删除测试数据卷。正式环境禁止删库重试，先备份、核对现场，再按发布手册处理。

### 10.9 构建报 `Unknown host repo.maven.apache.org`

这是 **Docker 构建容器的 DNS 不可用**，不是 Maven 依赖不存在。宿主机能上网（pip、curl 正常）不代表构建容器能解析域名。按顺序处理：

1. 用构建基础镜像验证容器 DNS：

   ```bash
   docker run --rm maven:3.9-eclipse-temurin-25 \
     sh -c 'getent hosts maven.aliyun.com || echo DNS_FAIL'
   ```

2. 输出 `DNS_FAIL` 时，给 `/etc/docker/daemon.json` 合并 DNS 并重启 Docker：

   ```json
   {
     "dns": ["223.5.5.5", "119.29.29.29"]
   }
   ```

   ```bash
   systemctl restart docker
   ```

3. 确认 Dockerfile 已复制仓库的 Maven 镜像配置：

   ```bash
   grep -n 'COPY .mvn/settings.xml /root/.m2/settings.xml' shop-backend/Dockerfile
   ```

   没有就在 `WORKDIR /app` 下面补这一行。

4. 清掉失败构建留下的“依赖不存在”缓存，再重建：

   ```bash
   docker builder prune -a -f
   docker compose --env-file .env.prod -f docker-compose.prod.yml build --progress plain backend
   ```

5. 镜像源优先用阿里云：`maven.aliyun.com` 返回 IPv4，容器可直接访问；`mirrors.cloud.tencent.com` 和 `repo.maven.apache.org` 可能只返回 IPv6，容器没有 IPv6 出口时会卡在连接阶段。

日志出现 `Downloading from aliyunmaven: https://maven.aliyun.com/...` 就说明镜像已生效。

## 11. 安全红线

- `.env.prod`、证书私钥、微信支付私钥、API v3 Key、管理员密码**永不提交 Git、永不发群、永不写进教程**。
- 公网只开 22、80、443、面板端口；3306、6379、8085 不对外开放。
- 宝塔面板不要用默认 8888，开启防火墙和告警。
- 管理员首次登录后立即改密码；客户交接后收回开发者账号和密钥。
- 预演环境的数据库密码与正式环境分开；正式上线前重新生成。
- 上线后保留上一版本镜像和配置，确认回滚路径可用。
