# 陕铺商城操作手册（服务器 + 小程序）

> 部署目录：`/www/shop`
> 管理后台：`https://bhtjl.top/`
> 小程序 API：`https://bhtjl.top/`
> 健康检查：`https://bhtjl.top/readyz`
> 当前模式：`catalog` 预演（不接真实支付）

**一句话：客户登录后台可以改商品和首页内容，不能改小程序代码；代码更新由开发团队发版。**

---

## 0. 最短版

- 客户：登录 `https://bhtjl.top/`，改商品、分类、库存、素材、首页内容，保存后小程序刷新即可。
- 运维：`shopcompose ps`、`curl -fsS https://bhtjl.top/readyz`、每天备份、证书到期前续期。
- 代码更新：备份 → `git pull` → 构建 backend/admin → 有迁移先 migrate → `up -d` → 验证。
- 小程序更新：改版本号 → `build_miniapp_release.py` → 微信开发者工具上传 → 提交审核 → 发布。

---

## 1. 角色分工

| 角色 | 负责什么 | 是否要重新发版 |
|------|----------|----------------|
| 客户 / 运营 | 改商品、分类、库存、素材、评论、Banner、频道、品牌、专题、店铺展示、可视化装修 | 不需要，保存后小程序刷新即可 |
| 开发 / 运维 | 改代码、发小程序新版本、改支付/物流/服务器配置 | 需要重新构建、上传、审核 |

客户能改的是“数据”，不是“小程序程序本身”。

- 新增页面、改交互、改支付流程、改页面代码：必须开发团队发新版本。
- 改商品价格、库存、图片、分类、首页 Banner：客户自己在后台改。

## 2. 客户日常操作

### 2.1 登录后台

1. 浏览器打开 `https://bhtjl.top/`。
2. 账号：`admin`。
3. 密码：服务器 `/www/shop/.env.prod` 里的 `DELIVERY_ADMIN_PASSWORD`。

查看密码：

```bash
cd /www/shop
grep '^DELIVERY_ADMIN_PASSWORD=' .env.prod
```

首次登录后立即修改密码。

### 2.2 给客户单独开账号

不要直接把超级管理员账号交给客户。

1. 系统管理 → 角色权限：确认或新建“商品运营”角色，勾选需要的权限。
2. 系统管理 → 管理员账号：新增客户账号，绑定“商品运营”角色。
3. 客户用自己的账号登录。
4. 交接完成后，停用或改掉 `admin` 的密码。

### 2.3 客户可以改什么

| 菜单 | 可改内容 |
|------|----------|
| 商品管理 → 商品列表 | 新增/编辑商品、价格、库存、上下架 |
| 商品管理 → 分类管理 | 商品分类、图标、排序 |
| 商品管理 → 库存工作台 | 库存、批量调库存 |
| 商品管理 → 素材库 | 上传图片、查看引用数、删除未被引用的图片 |
| 商品管理 → 评论管理 | 查看、审核、删除评论 |
| 内容管理 → Banner / 频道 / 品牌 / 专题 | 首页展示内容、图片、排序、状态 |
| 内容管理 → 店铺展示设置 | 店铺名称、Logo、公告等 |
| 实时预览与编辑 | 首页可视化装修，改 Banner、频道、品牌、专题 |

### 2.4 改完怎么生效

- 商品、分类、库存、Banner 等保存后，小程序重新进入页面或下拉刷新即可看到。
- 不需要重新提交小程序审核。
- 小程序端如果还显示旧数据，先退出小程序再进，或检查内容是不是“已发布/启用”状态。

### 2.5 图片怎么加

后台 → 商品管理 → 素材库 → 上传图片。

- 支持 JPG、PNG、WebP。
- 默认单张不超过 5MB（`MATERIAL_MAX_SIZE`）。
- 上传后图片地址是 `https://bhtjl.top/uploads/material/...`。
- 商品主图、轮播图、详情图都从素材库选择，不要填外部图片链接。

如果上传失败，先看服务器素材目录权限：

```bash
cd /www/shop
stat -c '%u:%g %n' deploy/data/material
```

期望 `10001:10001`。不是就执行一次：

```bash
cd /www/shop
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm --no-deps --user 0 --entrypoint sh backend \
  -c 'chown -R 10001:10001 /app/material'
```

### 2.6 客户不要做的事

- 不要删除已经有订单的商品，用“下架”代替。
- 不要改服务器、数据库、`.env.prod`、证书、支付参数。
- 不要把管理员账号密码发到群里。
- 不要在前台还没正式接支付时让真实客户下单付款。

## 3. 服务器日常运维

以下命令在服务器执行，默认目录 `/www/shop`。

### 3.1 进入目录并设置别名

```bash
cd /www/shop
alias shopcompose='docker compose --env-file .env.prod -f docker-compose.prod.yml'
```

新开终端后如果提示 `shopcompose: command not found`，重新执行上面两行。

如果服务器还没有 `.venv-delivery`（交付脚本的 Python 环境），先建一次：

```bash
cd /www/shop
python3 -m venv .venv-delivery
.venv-delivery/bin/pip install -U pip
.venv-delivery/bin/pip install -r scripts/requirements-delivery.txt
```

### 3.2 看服务状态

```bash
shopcompose ps
```

正常情况下五个容器都在运行：

```text
shop-mysql-1     healthy
shop-redis-1     healthy
shop-backend-1   healthy
shop-admin-1     running
shop-nginx-1     running
```

健康检查：

```bash
curl -fsS https://bhtjl.top/healthz
curl -fsS https://bhtjl.top/readyz
```

- `/healthz` 返回 `ok`：Nginx 正常。
- `/readyz` 返回 `{"status":"UP"}`：后端和数据库正常。

### 3.3 看日志

```bash
shopcompose logs --tail=100 backend
shopcompose logs --tail=100 nginx
shopcompose logs -f --tail=200 backend
```

`-f` 是持续看日志，按 `Ctrl+C` 只退出日志查看，不会停止服务。

### 3.4 重启

只重启后端：

```bash
shopcompose restart backend
```

全部重新拉起：

```bash
shopcompose up -d --wait --wait-timeout 300
```

服务器重启后，如果服务没起来：

```bash
systemctl is-enabled docker
cd /www/shop
shopcompose up -d --wait --wait-timeout 300
```

### 3.5 磁盘和日志

```bash
df -h
docker system df
```

磁盘快满时，先确认没有回滚需求，再清理悬空镜像：

```bash
docker image prune -f
```

不要直接删 `deploy/data`、`deploy/secrets`、`deploy/backups`。

### 3.6 证书

查看证书有效期：

```bash
cd /www/shop
openssl x509 -in deploy/secrets/tls/fullchain.pem -noout -subject -dates
```

替换新证书后：

```bash
shopcompose restart nginx
```

证书到期前 30 天续期，续期后替换 `fullchain.pem` 和 `privkey.pem`，再重启 Nginx。

### 3.7 端口

公网只保留：

- 22（SSH）
- 80 / 443
- 宝塔面板端口

不要对公网开放 3306、6379、8085。

## 4. 备份与恢复

### 4.1 手动备份数据库

```bash
cd /www/shop
mkdir -p deploy/backups/mysql
shopcompose exec -T mysql sh -c \
  'export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"; exec mysqldump -uroot --single-transaction --routines --triggers --default-character-set=utf8mb4 "$MYSQL_DATABASE"' \
  > "deploy/backups/mysql/manual-$(date +%Y%m%d-%H%M).sql"
ls -lh deploy/backups/mysql/
```

### 4.2 数据库 + 素材成套备份

```bash
cd /www/shop
.venv-delivery/bin/python scripts/delivery_backup.py backup \
  --env .env.prod \
  --database shop \
  --archive "deploy/backups/shop-$(date +%Y%m%d-%H%M).zip"
```

这个脚本会短暂停止 backend，备份数据库和 `deploy/data/material`，完成后自动启动 backend。建议在凌晨执行。

校验备份：

```bash
.venv-delivery/bin/python scripts/delivery_backup.py verify \
  --archive deploy/backups/shop-YYYYMMDD-HHMM.zip
```

加密后下载到本地或对象存储：

```bash
openssl enc -aes-256-cbc -pbkdf2 -salt \
  -in deploy/backups/shop-YYYYMMDD-HHMM.zip \
  -out deploy/backups/shop-YYYYMMDD-HHMM.zip.enc
```

备份文件不要只留在服务器上。

### 4.3 每天自动备份

宝塔面板 → 计划任务 → 新增 Shell 脚本，每天凌晨 3 点执行：

```bash
#!/bin/bash
cd /www/shop || exit 1
STAMP=$(date +%Y%m%d-%H%M)
.venv-delivery/bin/python scripts/delivery_backup.py backup \
  --env .env.prod \
  --database shop \
  --archive "deploy/backups/shop-${STAMP}.zip" \
  >> deploy/logs/backup.log 2>&1
find deploy/backups -name 'shop-*.zip' -mtime +7 -delete
```

保留最近 7 天，重要备份另外转存。

### 4.4 恢复

恢复只允许恢复到新的隔离库，不能直接覆盖生产库：

```bash
cd /www/shop
.venv-delivery/bin/python scripts/delivery_backup.py restore \
  --env .env.prod \
  --database shop_restore_20261125 \
  --archive deploy/backups/shop-YYYYMMDD-HHMM.zip \
  --material deploy/data/material_restore_20261125
```

恢复后核对商品、图片、订单金额。确认无误后，再决定是否切换。

## 5. 代码更新（开发团队执行）

> 客户不需要看这一节。

### 5.1 更新前先备份

```bash
cd /www/shop
git rev-parse HEAD
TAG=$(date +%Y%m%d-%H%M)

docker tag shanpu/backend:local shanpu/backend:$TAG
docker tag shanpu/admin:local shanpu/admin:$TAG
echo $TAG
```

再执行一次第 4.2 节的成套备份。

### 5.2 拉取新代码

```bash
cd /www/shop
git fetch --all
git checkout main
git pull
git rev-parse HEAD
```

如果 `/www/shop` 不是 Git 仓库，看 5.6 的 ZIP 方式。

### 5.3 构建新镜像（后端在服务器，前端在本机）

> 硬性限制：2 核 1.9G 的服务器**只能构建后端**（Maven 峰值约 1.2G，swap 能兜住）。管理后台的 Node 打包峰值超过 2G，会把内存打满转入 swap 抖动，表现是端口可连但 SSH 握手无响应、宝塔面板打不开，只能从云控制台强制重启，该现象已实测复现两次。因此生产 compose 的 admin 服务指向 `Dockerfile.prebuilt`，服务器上不再跑 Node，只 COPY 已构建好的 dist。

构建和启动都是长任务，不要接 `| tail` 之类的管道（会缓冲到结束才输出，看起来像卡死）。先把下面的心跳函数粘到当前终端：

```bash
watch_run() {
  local name="$1"; shift
  local log="/tmp/${name}-$(date +%m%d-%H%M%S).log"
  echo "日志: $log"
  "$@" > "$log" 2>&1 &
  local pid=$!
  while kill -0 $pid 2>/dev/null; do
    sleep 10
    printf '[%s] %6s mem=%s swap=%s | %s\n' "$(date +%H:%M:%S)" \
      "$(du -h "$log" | cut -f1)" \
      "$(free -m | awk '/Mem:/{print $3"MB"}')" \
      "$(free -m | awk '/Swap:/{print $3"MB"}')" \
      "$(tail -1 "$log" | tr -d '\r' | cut -c1-70)"
  done
  wait $pid; local rc=$?
  echo "===== EXIT=$rc | $log ====="
  [ $rc -ne 0 ] && tail -40 "$log"
  return $rc
}
```

#### 5.3.1 后端：在服务器构建

```bash
cd /www/shop
watch_run build-backend docker compose --env-file .env.prod -f docker-compose.prod.yml \
  build --no-cache --progress=plain backend
```

正常输出会依次出现：下载依赖 → `Compiling 80 source files` → `exporting layers` → `Image shanpu/backend:local Built`，耗时 1~2 分钟，`EXIT=0` 即成功。

若只用了 10 秒、日志仅几 KB 就结束，说明命中了旧缓存，镜像里不是新代码，必须加 `--no-cache` 重跑。

#### 5.3.2 管理后台：在本机 Mac 构建，只上传 dist

**第一步，在开发机的仓库根目录执行：**

```bash
cd shop-admin
pnpm install --frozen-lockfile   # 首次或依赖变更时执行
pnpm build
ls -lh dist && tar czf ~/Desktop/admin-dist.tar.gz -C dist .
```

约 13 秒完成，产物 3.3MB，压缩后约 1.1MB。

**第二步，把 `admin-dist.tar.gz` 传到 `/www/shop/`（宝塔文件管理器上传），然后解压到位：**

```bash
cd /www/shop
rm -rf shop-admin/dist && mkdir -p shop-admin/dist
tar xzf admin-dist.tar.gz -C shop-admin/dist
rm -f admin-dist.tar.gz
ls shop-admin/dist
```

**第三步，构建镜像（秒级，仅 COPY）：**

```bash
cd /www/shop
watch_run build-admin docker compose --env-file .env.prod -f docker-compose.prod.yml build admin
```

生产 compose 已指定 `shop-admin/Dockerfile.prebuilt`，它只做 `COPY dist`，镜像里不含 Node，**即使误操作也只会 COPY 失败，不会进入打包流程**。

**第四步，只重启 admin 容器：**

```bash
cd /www/shop
watch_run up-admin docker compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-build admin
```

后端也一起变了的话，把最后一行换成：

```bash
watch_run up docker compose --env-file .env.prod -f docker-compose.prod.yml \
  up -d --no-build --wait --wait-timeout 300
```

> 两个前提：`shop-admin/dist` 不存在或为空时构建会立即报错（这是有意的安全网，不会拖垮服务器）；`dist` 不在仓库里，首次部署或换服务器时必须先在本机构建上传一次。

### 5.4 有数据库迁移时

先停后端，执行迁移，再启动：

```bash
cd /www/shop
shopcompose stop backend
.venv-delivery/bin/python scripts/prepare_database.py migrate --env .env.prod --database shop
shopcompose up -d --wait --wait-timeout 300
```

没有新迁移就跳过 `stop` 和 `migrate`，直接：

```bash
shopcompose up -d --wait --wait-timeout 300
```

### 5.5 更新后验证

```bash
shopcompose ps
curl -fsS https://bhtjl.top/readyz
curl -fsS https://bhtjl.top/app-api/goods/count
curl -sS -o /dev/null -w 'admin=%{http_code}\n' https://bhtjl.top/
shopcompose logs --tail=100 backend
```

预期：五个容器全部 `Healthy`，`readyz` 返回 `{"status":"UP",...}`，`goods/count` 返回商品数，`admin=200`。

确认后台跑的是新包：对比本机 `shop-admin/dist/index.html` 里引用的入口 JS，与下面命令取到的文件名是否一致。

```bash
curl -sS https://bhtjl.top/ | grep -o 'static/js/[^"]*' | head -1
```

再登录后台，检查这次改动涉及的页面；小程序端也重新进入看一遍。

> 换了前端包后，所有用过后台的人必须**先退出登录再重新登录**。菜单权限是登录时写入浏览器 localStorage 的，旧登录态会继续按旧权限渲染，表现为「同事能看到某个菜单，我这里看不到」，而实际数据库权限是正常的。

### 5.6 ZIP 上传方式

如果服务器上的代码是 ZIP 上传的，不要删除 `/www/shop`，因为 `.env.prod`、`deploy/secrets`、`deploy/data` 都在里面。

本地打包时排除运行数据和构建产物：

```bash
cd /path/to/wechatMiniprogram_Store
zip -r shop-update.zip . \
  -x '.git/*' '*/node_modules/*' 'shop-admin/dist/*' \
     'shop-miniapp/unpackage/*' '*/target/*' '.venv-delivery/*' \
     'deploy/data/*' 'deploy/secrets/*' 'deploy/logs/*' \
     'deploy/backups/*' '.env.prod'
```

上传到 `/www` 后覆盖解压：

```bash
cd /www/shop
unzip -o /www/shop-update.zip
```

然后按 5.3.1 在服务器构建后端、5.3.2 在本机构建管理后台，再按 5.4 启动。

### 5.7 回滚应用

只回滚应用、保留当前数据库：

1. 编辑 `.env.prod`：

```env
SHOP_BACKEND_IMAGE=shanpu/backend:20261125-0900
SHOP_ADMIN_IMAGE=shanpu/admin:20261125-0900
```

2. 启动旧镜像：

```bash
shopcompose up -d --no-build backend admin
curl -fsS https://bhtjl.top/readyz
```

3. 验证完成后，把 `.env.prod` 改回：

```env
SHOP_BACKEND_IMAGE=shanpu/backend:local
SHOP_ADMIN_IMAGE=shanpu/admin:local
```

如果这次更新改了数据库结构，只回滚镜像不够，必须用备份在隔离库恢复验证，不能直接覆盖生产库。

## 6. 小程序发布与更新（开发团队执行）

### 6.1 微信公众平台一次性配置

登录 [微信公众平台](https://mp.weixin.qq.com)：

| 位置 | 配置 |
|------|------|
| 开发管理 → 开发设置 → 服务器域名 | request、uploadFile、downloadFile 合法域名都填 `https://bhtjl.top` |
| 开发管理 → 开发设置 → 开发者ID | 确认 AppID，生成 AppSecret |
| 设置 → 基本设置 | 小程序名称、头像、服务类目、简介 |
| 设置 → 服务内容声明 | 用户隐私保护指引 |
| 管理 → 成员管理 | 添加体验成员 |
| 设置 → 基本设置 → 小程序备案 | 完成小程序备案 |

注意：

- 域名必须已备案，必须是 HTTPS。
- 开发者工具的“不校验合法域名”只对模拟器有效，真机体验版仍会校验。
- `shop-miniapp/manifest.json`、`shop-miniapp/project.config.json` 和微信公众平台的 AppID 必须一致。

### 6.2 构建体验版

在开发机执行：

```bash
cd /Users/leo/Desktop/Project/wechatMiniprogram_Store

python3 scripts/build_miniapp_release.py \
  --cli /Applications/HBuilderX.app/Contents/MacOS/cli \
  --api-root https://bhtjl.top/ \
  --environment staging
```

- macOS 的 HBuilderX CLI 默认在 `/Applications/HBuilderX.app/Contents/MacOS/cli`。
- `--api-root` 只填根域名，不要带 `/app-api/`。
- 体验版用 `staging`，正式版用 `production`。

### 6.3 上传体验版

用 HBuilderX 打开 `shop-miniapp`，发行 → 小程序-微信，选择微信开发者工具上传。

也可以用微信开发者工具 CLI：

```bash
/Applications/wechatwebdevtools.app/Contents/MacOS/cli upload \
  --project "$(pwd)/shop-miniapp/unpackage/dist/build/mp-weixin" \
  --version 1.0.1 \
  --desc "体验版-20261125"
```

然后到微信公众平台 → 管理 → 版本管理：

1. 把刚上传的版本设为体验版。
2. 添加体验成员微信号。
3. 用真机扫码验证。

### 6.4 正式版发布

1. 把 `--environment` 改成 `production` 重新构建。
2. 上传到微信公众平台。
3. 版本管理 → 提交审核。
4. 审核通过后点击发布。

代码、页面、交互、支付流程有改动，都必须重新提审；只改商品和首页内容不需要。

## 7. 正式收款前：catalog 切换 commerce

当前是 `catalog` 预演模式，不能收真实货款。客户要正式收款前，确认已经有：

- 微信支付商户号
- 商户 API 证书 `apiclient_key.pem`
- 平台证书 `platform_cert.pem`
- API v3 Key
- 快递100 的 customer 和 key

把证书放到：

```text
/www/shop/deploy/secrets/wechat-pay/apiclient_key.pem
/www/shop/deploy/secrets/wechat-pay/platform_cert.pem
```

权限：

```bash
chmod 600 deploy/secrets/wechat-pay/apiclient_key.pem deploy/secrets/wechat-pay/platform_cert.pem
```

修改 `.env.prod`：

```env
APP_DELIVERY_MODE=commerce
```

## 8. 常见问题

### 8.1 打开后台 502

```bash
cd /www/shop
shopcompose ps
shopcompose logs --tail=100 backend
shopcompose logs --tail=100 nginx
curl -fsS https://bhtjl.top/readyz
```

多数是 backend 没起来或数据库连接失败。

### 8.2 证书无效

```bash
openssl x509 -in deploy/secrets/tls/fullchain.pem -noout -subject -dates
openssl x509 -in deploy/secrets/tls/fullchain.pem -noout -pubkey | openssl sha256
openssl pkey -in deploy/secrets/tls/privkey.pem -pubout | openssl sha256
```

两个 SHA256 必须一致；`fullchain.pem` 必须是完整证书链。

### 8.3 小程序请求失败

按顺序检查：

1. 微信公众平台服务器域名是否填了 `https://bhtjl.top`。
2. 域名是否备案。
3. 证书是否有效。
4. 真机浏览器能否打开 `https://bhtjl.top/readyz`。
5. 小程序构建时 `--api-root` 是否写成了 `https://bhtjl.top/`。

### 8.4 小程序登录失败

检查 `.env.prod`：

```bash
grep -E '^WX_MA_(APPID|SECRET)=' .env.prod
```

- `WX_MA_APPID` 必须和小程序 AppID 一致。
- `WX_MA_SECRET` 必须是当前有效的 AppSecret。
- 改完重启后端：

```bash
shopcompose up -d backend
```

### 8.5 上传图片失败

- 图片是否超过 5MB。
- 是否 JPG/PNG/WebP。
- `deploy/data/material` 属主是否为 `10001:10001`。
- 后端日志有没有 `素材文件保存失败`。

### 8.6 构建报 `Unknown host repo.maven.apache.org`

这是 Docker 构建容器 DNS 问题，不是 Maven 仓库挂了。

1. 测试容器 DNS：

```bash
docker run --rm maven:3.9-eclipse-temurin-25 \
  sh -c 'getent hosts maven.aliyun.com || echo DNS_FAIL'
```

2. 如果输出 `DNS_FAIL`，给 `/etc/docker/daemon.json` 加：

```json
{
  "dns": ["223.5.5.5", "119.29.29.29"]
}
```

然后：

```bash
systemctl restart docker
```

3. 确认 Dockerfile 有 Maven 镜像配置：

```bash
grep -n 'COPY .mvn/settings.xml /root/.m2/settings.xml' shop-backend/Dockerfile
```

没有就在 `WORKDIR /app` 下面补这一行。

4. 清理失败缓存后重建：

```bash
docker builder prune -a -f
docker compose --env-file .env.prod -f docker-compose.prod.yml build --progress plain backend
```

### 8.7 磁盘满了

```bash
df -h
docker system df
docker image prune -f
```

不要删 `deploy/data`、`deploy/secrets`、`deploy/backups`。

### 8.8 后台商品、分类、评论都是空的

`prepare_database.py initialize` 初始化新库时会清空演示业务数据，这是正常的。

预演阶段要演示数据，可以重新导入：

```bash
cd /www/shop
docker compose --env-file .env.prod -f docker-compose.prod.yml exec -T mysql \
  sh -c 'export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"; exec mysql -uroot --default-character-set=utf8mb4 "$MYSQL_DATABASE"' \
  < sql/migrations/V20260801_02__product_demo_seed.sql
```

正式交付前不要保留演示数据。

## 附录：从零部署 / 换服务器

只在新建服务器时使用。已有 `/www/shop` 不要重复执行。

1. 安装 Docker、Docker Compose，确认 80/443 没被宝塔 Nginx 占用。
2. 上传代码到 `/www/shop`。
3. 创建目录：

```bash
cd /www/shop
mkdir -p deploy/secrets/tls deploy/secrets/wechat-pay \
  deploy/data/mysql deploy/data/redis deploy/data/material \
  deploy/logs/backend deploy/logs/nginx deploy/backups/mysql
chmod 700 deploy/secrets
```

4. 放证书：

```text
deploy/secrets/tls/fullchain.pem
deploy/secrets/tls/privkey.pem
```

```bash
chmod 600 deploy/secrets/tls/fullchain.pem deploy/secrets/tls/privkey.pem
```

5. 生成配置：

```bash
.venv-delivery/bin/python scripts/configure_delivery.py --domain bhtjl.top
chmod 600 .env.prod
```

6. 构建镜像：

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml build backend
docker compose --env-file .env.prod -f docker-compose.prod.yml build admin
```

7. 启动数据库：

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d mysql redis
```

8. 初始化数据库：

```bash
export DELIVERY_ADMIN_PASSWORD="$(grep -E '^DELIVERY_ADMIN_PASSWORD=' .env.prod | cut -d= -f2-)"
.venv-delivery/bin/python scripts/prepare_database.py initialize --env .env.prod --database shop
unset DELIVERY_ADMIN_PASSWORD
```

9. 修正目录属主：

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml run --rm --no-deps --user 0 --entrypoint sh backend \
  -c 'chown -R 10001:10001 /app/material /app/logs'
```

10. 启动全部服务并验证：

```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --wait --wait-timeout 300
curl -fsS https://bhtjl.top/healthz
curl -fsS https://bhtjl.top/readyz
```
